This module fixes two interfaces that everyone else's code depends on:

1. **The LLM wrapper signature** (`infra/llm.py`): one `LLMClient.call(...)` used by
   every role, returning one plain-dict record per logical call. A scripted
   `MockBackend` is the scripted offline backend; `GeminiBackend` is the live one on
   the google-genai SDK, with measured usage and cost (see "Live backend" below).
2. **The per-game event log** (`infra/eventlog.py`, `schemas/event_log.schema.json`):
   an append-only JSONL file per game, a validator, a cost summary, and the export to
   Josh's exchange format in `examples/annotation_example.json`, which his
   `casework.diagnostics` adapters consume.

Standard library only except the live backend (google-genai, imported on first use),
plain dicts at module boundaries; tests and examples make no API calls and spend
nothing (Josh's conventions). Run everything from the repository root.

## LLM wrapper

```python
from infra import LLMClient, MockBackend, EventLog

log = EventLog("runs/pilot_run/game_001.jsonl", game_id="game_001")
llm = LLMClient(MockBackend(), model_id="mock-model", decoding={"temperature": 0.7, "seed": 7,
                "max_output_tokens": 256}, log=log, pricing=None)

record = llm.call(role="detective", purpose="question", phase="through_first_accusation",
                  messages=[{"role": "system", "content": system_prompt},
                            {"role": "user", "content": user_prompt}],
                  game_id="game_001", response_schema=DETECTIVE_ACTION_SCHEMA)
record["text"]      # raw model output, always present
record["parsed"]    # JSON value when response_schema was given and valid, else None
record["call_id"]   # "c000017": cite it in the controller event for this step
```

`call()` keyword arguments:

| Argument | Meaning |
|---|---|
| `role` | `detective`, `suspect`, `interpreter`, `extractor`, `annotator`: which prompt family generated |
| `purpose` | `detective_decision` (the game loop's single decide call, a question or an accusation depending on the output; the `accusation` event's `call_id` says which), `question`, `accusation`, `interrogation_response`, `invitation`, `acceptance`, `conversation_message`, `conversation_reply`, `intent_interpretation`, `ledger_extraction`, `annotation`. The contradiction report is not a purpose: it rides on the first `accusation` call (Aravindh's action schema, proposal 5.3) |
| `agent_id` | Stable persona across games (decisions.md D3): `suspect_1`..`suspect_5` in `public["suspects"]` order for `role="suspect"` (required; `infra.suspect_agent_ids(public["suspects"])` or Harish's `agent_ids_for(case)` gives the mapping), and the role itself for the singleton agents `detective`, `interpreter`, `extractor`, `annotator` (the default when omitted). Anything else is rejected |
| `phase` | `through_first_accusation`, `accusation_retries`, `post_game_analysis` (proposal 5.2 cost buckets; the first accusation call itself is in the first bucket) |
| `messages` | `[{"role": "system"\|"user"\|"assistant", "content": str}]`; build them fresh every call (proposal 4.2) |
| `game_id` | Copied onto the record; must match the log's game |
| `response_schema` | Optional JSON-schema-like dict; enables parsing, shape checking and the bounded format repair |
| `max_output_tokens` | Per-call cap; defaults to `decoding["max_output_tokens"]` |
| `tags` | Free dict for cross-references (for example `{"decision_index": 4}`) |

The record (also the `llm_call` event) holds: `call_id`, `game_id`, `role`, `agent_id`, `purpose`,
`phase`, `model_id`, `decoding`, `response_schema`, `max_output_tokens`, `messages`,
`text`, `parsed`, `usage` `{input_tokens, output_tokens, reasoning_tokens, total_tokens}`,
`cost_usd` (None without pricing), `finish_reason`, `model_version` (the served version
reported by the provider, None for mocks), `latency_ms`, `attempts[]`,
`repair_used`, `status`, `tags`. Prompts are retained in full so a game can be
replayed and audited; logs therefore contain private case text and never leave `runs/`.

Policy, fixed here so every role behaves the same:

- **Transport failures** (`TransportError`: timeouts, rate limits, 5xx) are retried at
  most `max_transport_retries=3` times with backoff `(1, 2, 4)` seconds.
- **Formatting failures** (unparseable or wrong-shape JSON when `response_schema` is
  given) get exactly `max_format_repairs=1` repair attempt: the bad output is appended
  as an assistant turn plus a fixed repair instruction. Testimony text is never edited.
- Every attempt is recorded in `attempts[]` with `kind` (`initial`, `transport_retry`,
  `format_repair`), `status`, its own `usage` and `latency_ms`, so repair and retry
  tokens stay separable (proposal 3.5, 5.2, 5.4). The record's `usage` is the sum.
- When the bounds are exhausted the record is still written (`status` =
  `transport_failure` or `format_failure`) and `LLMCallError` is raised with the
  record attached. The controller catches it, emits `failure` and ends the game with
  `game_end(outcome="failed_run")`. Unresolved failures stay in operational accounting.
- `pricing` = `{"input_per_million", "output_per_million", optional
  "reasoning_per_million", "basis"}` gives `cost_usd` per record; copy the same dict
  into `game_start` so the pricing basis is on file. Without it `cost_usd` is `None`,
  never a silent zero.

Backends implement `generate(model_id=, messages=, decoding=, response_schema=,
max_output_tokens=) -> {"text", "usage": {input_tokens, output_tokens,
reasoning_tokens}, "finish_reason"}` and raise `TransportError` for retryable errors.
`MockBackend(script)` consumes a list in order (str -> text, dict -> JSON text,
exception instance -> raised) or calls a function of the request; its usage is a
character-count estimate and must never be reported as measured tokens.
`GeminiBackend` is described in the next section.

## Live backend (Gemini)

`GeminiBackend(api_key=None, api_key_env="GEMINI_API_KEY", timeout_s=60, client=None)` wraps
`google-genai` (pinned in `requirements.txt`) and imports it on first use, so `import infra`
works without it. The key is read from the environment only; nothing in the repo holds it.
`examples/gemini_smoke.py` also loads a git-ignored `.env` in the repo root if present.

| Wrapper input | SDK field |
|---|---|
| system messages | `config.system_instruction` (joined) |
| user / assistant messages | `contents` with roles `user` / `model`, one text part each |
| `decoding.temperature`, `top_p`, `seed`, `max_output_tokens` | `GenerateContentConfig` fields of the same name |
| `decoding.thinking_budget` | `thinking_config.thinking_budget` (2.5 models; `0` turns thinking off) |
| `decoding.thinking_level` | `thinking_config.thinking_level` (3.x models: `minimal`, `low`, `medium`, `high`) |
| `response_schema` | `response_mime_type="application/json"` plus `response_json_schema` (plain JSON Schema) |

| Record field | SDK source |
|---|---|
| `usage.input_tokens` | `usage_metadata.prompt_token_count` |
| `usage.output_tokens` | `usage_metadata.candidates_token_count` |
| `usage.reasoning_tokens` | `usage_metadata.thoughts_token_count` (billed at the output rate) |
| `finish_reason` | `candidates[0].finish_reason`, or `BLOCKED_<reason>` from `prompt_feedback` with empty text |
| `model_version` | `response.model_version` (keep it: the proposal asks for model identifiers) |

Retries: HTTP 408, 429 and 5xx (`errors.ServerError`), httpx transport errors and built-in

transient and must stop the run. The SDK's own retry option is left off so retries happen
in exactly one place. Set thinking explicitly in the frozen decoding settings before the
pilot (`thinking_level` on 3.x models). Availability check on 20 Oct 2026 with a fresh AI

## Event log

One file per game, `runs/<run_id>/<game_id>.jsonl`, one JSON object per line, written
and flushed on every `emit`, so a crashed run keeps everything up to the crash. Every
line starts with the envelope `seq` (1-based, contiguous), `ts` (UTC ISO 8601),
`game_id`, `kind`; the rest is flat, kind-specific.

ID conventions (enforced by `validate_events`):

| ID | Form | Rule |
|---|---|---|
| Detective-visible exchange | `e1`, `e2`, ... | t is the memory exchange index I_t of the proposal: interrogations and accepted detective conversations, in play order. `exchange_index` carries t as an integer |
| Interrogation turn | `interrogation_index` | Counts the turn budget only; separate from t |
| Invitation | `inv1`, `inv2`, ... | Identity-only events; never testimony |
| Private conversation | `p1`, `p2`, ... | Suspect-only; exported as `p1_msg` and `p1_reply` |
| Detective conversation | `conv1`, ... | Also carries `exchange_id` `e<t>` because it enters memory |
| LLM call | `c000001`, ... | Per-client counter; every controller event cites the calls it used |
| Agent | `detective`, `suspect_1`..`suspect_5`, `interpreter`, `extractor`, `annotator` | decisions.md D3; suspects numbered in `public["suspects"]` order, so the same ID means the same persona in every game of a case |

Event kinds, who emits them and when (proposal 4.1 loop):

| kind | Emitted by | When | Key fields |
|---|---|---|---|
| `game_start` | Orchestrator | Once, first | `run_id`, `case_id`, `case_sha256`, `condition`, `k`, `turn_budget`, `accusation_budget`, `seed`, `model_id`, `decoding`, `prompt_versions`, `pricing`, `manifest_sha256`, `code_version` |
| `llm_call` | `LLMClient` | Every call, automatically | the record above |
| `memory_view` | Aravindh's memory module / controller | Right after each detective call returns | `decision_index`, `decision_type` (`decision` for the loop's decide call, else `question`/`accusation`/`acceptance`/`conversation_reply`), `window_exchange_ids` (H_t), `memory_payload` (what was actually in the prompt), `call_id` |
| `interrogation` | Harish's loop | After the suspect reply is delivered | `interrogation_index`, `exchange_index`, `exchange_id`, `suspect`, `question`, `intent`, `allowed_branches`, `instructions`, `selected_branch_id`, `response` (unchanged), call IDs, `controller_matched` |
| `extraction` | Aravindh's ledger extractor | After each delivered exchange, ledger condition only | `exchange_id`, `call_id`, `status` (`ok`/`repaired`/`failed`), `entries`, `failure_entry` |
| `checkpoint_start` | Harish's scheduler | After interrogations 5, 10, 15 when gathering can continue | `checkpoint_index`, `after_interrogation`, `proposal_order`, `seed_used` |
| `invitation` | Scheduler | Each proposal, both passes | `invitation_id`, `pass_no`, `sender`, `recipient`, `decision` (`accepted`/`rejected`/`no_slot`), call IDs |
| `conversation` | Scheduler | Each completed message+reply | `conversation_id`, `visibility` (`private`/`detective`), `exchange_id`/`exchange_index` (detective only), `inviter`, `recipient`, `message`, `reply`, call IDs, `controller_matched` |
| `checkpoint_end` | Scheduler | End of the checkpoint | counts |
| `contradiction_report` | Controller | From the first accusation call's parsed output, logged just before that `accusation` event | `call_id` (the first accusation call), `window_exchange_ids`, `reported_pairs_raw` (Aravindh's `contradiction_report` field: exchange ID + quote citations) |
| `accusation` | Controller | Each of up to three attempts | `attempt`, `triple`, `valid`, `correct`, `feedback` (whole-triple only), `exchange_index`, `interrogations_used`, `testimony_frozen` |
| `failure` | Controller | On `LLMCallError`, context overflow, invalid action after repair | `stage`, `reason`, `call_id`, `detail` |
| `game_end` | Controller | Once, last | `outcome` (`solved_first`/`solved_retry`/`unsolved`/`failed_run`), `attempts_used`, `first_accusation_correct`, `component_correct`, counters, `cost` = `summarise_cost(events)`, `duration_s` |

`EventLog` has one typed helper per kind (`log.interrogation(...)`,
`log.accusation(...)`, ...) with keyword-only arguments; `exchange_id` is derived
from `exchange_index`. `emit(kind, **payload)` is the raw form; both reject unknown
kinds and missing required keys immediately, so a wiring mistake fails at the
controller rather than at analysis time.

`controller_matched` is online bookkeeping: the finite claim/lead/retraction IDs the
controller passed to Josh's `record_delivery` after matching the delivered text. It is
not an annotation and the exporter ignores it unless explicitly asked (below).
`allowed_branches`, `instructions` and `memory_payload` are controller/evaluator
records of what was supplied; none of them is detective input.

What the log guarantees for the proposal's requirements: responses stored byte-exact
(5.4), private conversations never share an `e<t>` ID (3.4), invitation and decision
calls are costed but consume no turn (3.4), testimony events after the first
accusation are rejected by the validator (3.5), repair and retry tokens are itemised
(3.5, 5.2), the memory view per decision is recorded (4.2), and `memory_payload`
can be checked against the model's context limit rather than truncated (4.2).

## Mapping to Josh's exchange format

`to_annotation_exchanges(events, overlay=None, until_first_accusation=True)` returns
`{"exchanges": [...], "reported_pairs": [...]}` with exactly the keys of
`examples/annotation_example.json`:

| Log event | Exported exchange |
|---|---|
| `interrogation` | `kind` `interrogation`, `speaker` = suspect, `delivered_response` = `response` |
| `conversation` with `visibility` `detective` | `kind` `detective_conversation`, `speaker` = inviter, `delivered_response` = `message`; the detective's reply stays in the log only (Josh's note: the full log keeps both messages) |
| `conversation` with `visibility` `private` | two exchanges `p<n>_msg` (inviter) and `p<n>_reply` (recipient), `kind` `suspect_conversation` |
| `invitation` | `kind` `invitation`, `speaker` = sender, empty `delivered_response` |
| `claim_ids`, `annotations` | from the annotation overlay; empty without one |
| `reported_pairs` | from the overlay (claim IDs resolved after play); the in-play citations stay in `contradiction_report.reported_pairs_raw` |

By default the export takes the trace prefix ending immediately before the first
accusation, which is what `evidence_diagnostics` and `contradiction_diagnostics`
expect. Exchanges keep play order, so `eligible_exchanges` can window them by position.

The **annotation overlay** is the proposed shape for Elena's checked labels, one file
per game:

```json
{"game_id": "game_001",
 "exchanges": {"e1": {"claim_ids": ["claim_cover_Blair"],
                      "annotations": [{"claim_id": "claim_cover_Blair",
                                       "source_span": {"start": 0, "end": 30, "text": "I was in the Library at 20:30."},
                                       "confidence": "manually_checked_mock"}]}},
 "reported_pairs": [{"left": {"exchange_id": "e1", "claim_id": "claim_cover_Blair"},
                     "right": {"exchange_id": "e2", "claim_id": "claim_witness_Blair"}}]}
```

Spans are Python character offsets into the exported `delivered_response`; the
exporter raises if a span does not match, if the overlay names an exchange that is not
in the trace, or if a reported pair cites an unknown exchange. Annotation of behaviour
beyond the finite claim catalogue (unsupported additions, refusals, follow-ups) is
Elena's rubric and needs its own fields; this overlay only carries what Josh's
adapters consume.

`claim_ids_from="controller_bookkeeping"` fills `claim_ids` from `controller_matched`
instead of an overlay. It exists so the metrics pipeline can be exercised on fake
transcripts before labels exist. It is a smoke test, never a source of reported numbers.

`examples/infra_example.py` shows the whole chain: with the overlay, the exported
`e1`/`e2`/`e3` entries equal Josh's fixture and his adapters return coverage 2/10,
candidate count 50 and contradiction precision and recall 1.0, the same numbers as
`examples/diagnostics_example.json`.

## Cost accounting

`summarise_cost(events)` totals tokens and USD by `role`, `agent_id`, `purpose`, `phase`
and attempt kind from the `llm_call` events, and `game_end.cost` stores it. The
`by_agent` table is what tracks one persona across games; `controller_repair_calls`
counts calls tagged `repair_of` (the controller-side detective repairs of D1). Phases split
cost through the first accusation, retry cost and post-game analysis as the proposal
asks; attempt kinds split retries and repairs. `cost_usd` is `None` when no call had
pricing, and `calls_without_pricing` says how many lacked it.

## Orchestration, transcripts and replay

`python -m infra run` plays a seeded run through `run_game`: Harish's
`controller.interfaces.run_game` with `--game controller`, or the stand-in
`infra.mockgame.run_game` (default) that plays a seeded mock game against Josh's case so
the pipeline can be exercised offline. A run is a folder:

```
runs/<run_id>/run.json                 plan written once: master seed, per-game seeds, shuffled order, config, case hash
runs/<run_id>/results.jsonl            one row per finished game, appended as games finish (crash-safe)
runs/<run_id>/<game_id>.jsonl          the event log
runs/<run_id>/<game_id>.transcript.md  readable transcript (private conversations marked)
runs/<run_id>/<game_id>.exchanges.json Josh-format exchanges with empty claim_ids, for Elena
```

- **Seeding and blocks.** Each game's seed is `sha256(master_seed:condition:repeat)`. Games
  are played in blocks of one game per condition, with the conditions shuffled inside each
  block by the master seed (proposal 5.5), so a run is reproducible from `run.json` alone
  and any stop leaves the conditions equal. Pass the game's `seed` to the scheduler's RNG
  and log it in `checkpoint_start.seed_used`.
- **Resume.** Running the same `--run-dir` again skips finished plan entries. `--limit-blocks N`
  plays at most N blocks now; `--dry-run` prints what is left.
- **Cost ceiling.** `--max-cost-usd` (default: the config's `budget_usd`) is checked only before
  a new block starts: once the summed `cost_usd` of finished games reaches it, no further block
  starts and the games of the current block finish, so a budget stop reduces every condition
  equally. `summary` reports `cost_per_game_usd` per condition for the early cost estimate.
- **Parallel games.** `--workers N` plays N games at once (threads; the work is I/O bound).
  The smoke test measured 8 to 35 s per call with 503/504 retries, so sequential runs of
  300 games would take days: plan on 4 to 8 workers and keep `timeout_s` above 60 in the
  config. Each game gets its own `LLMClient` (fresh call counter) and its own log file.
- **Accounting.** A `run_game` that raises becomes a results row with `status: crashed`
  and the error text; a game that ends with `game_end.outcome = failed_run` stays an
  unsuccessful game. `summary` reports both separately, and operational first-accusation
  accuracy counts them as failures (proposal 5.4). Every log is validated after the game
  and `validation_passed` is stored on the row, with `truncated_calls` (calls that ended with
  `finish_reason` `MAX_TOKENS`) so output caps that cut off a decision are visible per game.

**Contract for Harish's `run_game(case_path, config, seed, condition, llm, log_dir)`:**
it receives an `LLMClient` whose `log` is `None`; create
`EventLog(Path(log_dir) / f"{game_id}.jsonl", game_id)`, set `llm.log = log`, emit
`game_start` first, and return `{"game_id", "log_path", "outcome",
"first_accusations_correct"}`. `config` is the experiment config plus `run_id` and
`case_sha256`. The orchestrator reads outcome, counters and cost from the log's
`game_end`, so the return dict only needs to be right about `log_path`.

**Replay.** `python -m infra replay <log>` prints the transcript (`--no-private` hides
suspect-only conversations, `--write` writes the two artifact files, `--check` validates
the log). `infra.replay.ReplayBackend(events)` re-serves the recorded responses of one game
in call order through the normal `LLMClient`, with no API calls: a recorded failure is
replayed as the same number of transport errors, and a prompt that differs from the
recording raises `ReplayMismatch`, which is how a controller change that alters prompts
shows up. A recorded format repair replays as its final text in one attempt.

**Mock game caveats.** It picks intents, branches, invitations and accusations at random
from the seed, copies the chosen branch IDs into `controller_matched` (a live controller
must match delivered text instead), and its outcome odds are the same for every condition
on purpose, so nothing in it can look like a result.
Use it for plumbing, metrics code and labelling practice, never for results.

## Metrics, confidence intervals and figures

`python -m infra metrics <run_dir> [--case cases/evaluation.json] [--bootstrap 2000] [--seed 0] [--out DIR]`
reads a run folder (`results.jsonl` when the orchestrator wrote one, otherwise every game log in
the folder), builds one record per game and writes to `<run_dir>/analysis/`:

```
metrics.json      per-condition point estimates with 95% bootstrap CIs, pairwise differences, descriptions
metrics.md        the same as tables for the slides and report
per_game.csv      one row per game (every field below) for anyone's own analysis
figures/*.png|svg accuracy_by_condition, solve_rate_by_attempt, cost_per_game, efficiency_by_condition, ledger_minus_raw
```

- **Outcomes (proposal 5.1).** `first_accusation_accuracy` (A1), `culprit/weapon/location_accuracy`
  on the first attempt, `solve_rate_within_2` (A2), `solve_rate_within_3` (A3, eventual solve rate),
  `wrong_valid_accusation_rate` (wrong valid over all valid accusations, pooled),
  `attempts_used_mean_solved`. Operational rates count failed runs and crashes as unsuccessful
  (proposal 5.4); `first_accusation_accuracy_completed` restricts to games that reached a
  verdict and states its denominator. `failed_run_rate` and `crash_rate` are reported apart.
- **Interaction and efficiency (5.2).** `interrogations_before_first_accusation_mean`,
  `exchanges_total_mean`, `checkpoints_reached_mean`, `invitations_sent_mean`,
  `invitation_acceptance_rate`, `detective_conversations_mean`, `private_conversations_mean`,
  `contradiction_pairs_reported_mean` (count only; precision and recall need the annotation).
- **Cost (5.2).** `cost_usd_mean`, `cost_through_first_accusation_mean`,
  `cost_accusation_retries_mean`, tokens, reasoning tokens, transport retries, format repairs,
  controller repairs, calls cut off at the output cap, wall-clock seconds. A phase with no
  calls costs 0 for that game (so the retry mean averages over every game); `None` means the
  pricing was unknown, and the phase means add up to the total.
- **Heuristic coverage.** `online_evidence_coverage_mean` and `online_essential_coverage_mean`
  come from the controller's online claim matching (decisions.md D11), not from labels; they are
  the "clues heard" numbers used during the pilots. Label-based coverage, repeated questions and
  contradiction precision/recall are computed from Elena's annotation with Josh's adapters, not here.
- **Confidence intervals.** Percentile bootstrap, games resampled with replacement within each
  condition (default 2000 replicates, seeded), which is the proposal's descriptive 95% interval
  conditional on the one case. `differences` holds ledger minus raw, ledger minus none and raw
  minus none for A1, A3, turns, cost and coverage, each with its own bootstrap CI from
  independent resampling of the two conditions.
- **Figures** use fixed colours per condition (none blue, raw orange, ledger aqua, validated for
  colour-vision deficiency), neutral ink for every label, direct value labels and the CI as a bar
  through the point. matplotlib is an analysis-only dependency; without it the command still
  writes the JSON, CSV and Markdown.

## What this module does not do

Only the live backend makes API calls (never from tests, the mock game or the examples).
It does not play real games (the mock game stands in for Harish's controller), does not
schedule checkpoints,
does not interpret questions and does not compute the primary metrics. Those arrive
in later items and in the other owners' modules. The event log records what happened;
it never changes a delivered response, regenerates testimony or feeds annotations back
into a game.
